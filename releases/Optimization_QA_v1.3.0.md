# To-be Process Map v1.3.0 — 실행 최적화 및 QA

검토일: 2026-11-10. 기준: 이전 v1.2.0, 기존 CRM 입력·오류 예시, 팀의 실행 중단 메시지. 팀에서 실행한 196개 업무 후보 HTML·QC 로그는 제공되지 않았다.

## 진단

“이번 응답에서 쓸 수 있는 작업 횟수”는 에이전트 실행 플랫폼의 한도다. 이 메시지만으로 ZIP 파일이 커서 중단됐다고 판단할 수 없다. 설계 작성량, 반복 도구 호출, 브라우저 검사, 오류 수정 왕복이 함께 영향을 줄 수 있다. 기존 ZIP은 약 1.1 MiB였고, 실행에 쓰이지 않는 과거 예제가 큰 부분을 차지했다.

추가로 기존 QC는 작업자에서 검출한 레이아웃 실패 문자열을 최종 errors에 합쳤다. 이를 스크립트 예외 건수로 읽으면 잘못된 진단이 된다. 원본 로그가 없으므로 팀의 “6건”이 이 경우였다고 단정하지 않는다.

## 변경

1. **단일 실행 경로:** prepare → 설계 작성 → run. 생성·정적 검증·브라우저 QC·Excel/HTML 일치·certify를 run이 이어서 수행한다. 선택적 enrich는 synth/fill/absorb를 묶고 이전 설계를 백업한다.
2. **체크포인트·재개:** 상태, 입력/구현 해시, 후보 위치, 오류 전체 JSON을 저장한다. 동일한 통과 결과는 재사용한다. 입력·코드·브라우저/Playwright·검사 조건이 달라지면 무효화한다. 실패 결과를 통과로 바꾸지 않는다.
3. **백그라운드 작업:** run --background가 최대 900초 동안 검사와 인증을 이어간다. 모델이 상태를 짧은 간격으로 반복 조회할 필요가 줄어든다. 환경이 종료되면 저장 상태에서 재개한다.
4. **출력 위치 고정:** HTML·Excel 후보부터 outputs 아래 revisions 폴더에 생성한다. 마지막 응답에서 수동으로 파일을 옮기지 않는다. manifest가 passed인 현재 revision만 최종 경로로 제공한다.
5. **브라우저 비용 축소:** 화면 안정화 기준을 사용하고, 중복 순회와 대기를 합쳤다. 기본 작업자는 2개다. 통과한 동일 파일의 검사는 재사용하고, 동일 파일의 실행 문제 해결 후 --retry-qc로 실패한 묶음만 명시적으로 재시도할 수 있다. HTML을 수정했다면 전체 검사 대상이다.
6. **진단 강화:** 실제 JavaScript 예외, 레이아웃 실패, 작업자 실패를 구분한다. 관련 화면·노드·JSON 경로·stack·스크린샷으로 원인을 좁힌다. 표준 출력은 최대 8개 이슈이며 전체 내역은 JSON에 저장한다.
7. **렌더 사전검증:** Agent 페이지, 흐름 설명, 데이터·시스템·AX 배열 등의 잘못된 구조를 브라우저 전에 검출한다. 정상적인 story.imp의 선택적 3번째 참조 목록은 허용한다. 필수 내용을 임의로 채우지 않는다.
8. **생성 비용 축소:** 같은 빌드 안에서 검증·합성 결과를 재사용하고, Excel 생성·HTML 일치 검증을 한 번의 workbook 열기로 수행한다. 마지막 인증의 독립적인 검증은 유지한다.
9. **클라이언트 패키지 경량화:** 실행에 쓰이지 않는 과거 부문 JSON·대형 참고 HTML·장황한 과거 이력을 제외했다. 엔진·HTML 템플릿·공통 문구 자산의 SHA256은 v1.2와 동일하다.

## 측정과 검증

| 항목 | 이전 | 최적화 | 판정 |
|---|---:|---:|---|
| 같은 정상 HTML의 최종 브라우저 QC | 34.131초 | 10.922초 | 24개 화면·7개 상세 창, 모든 요약 지표 동일 |
| 같은 HTML QC 재호출 | 전체 새 실행 | 0.032초 | 같은 해시·실행조건의 통과 결과, 새 브라우저 실행 없음 |
| 정상 예제 배포 빌드 중앙값(3회) | 0.0900초 | 0.0522초 | 약 42% 감소, 표 데이터 동일 |
| 실제 CRM Excel export 중앙값(3회) | 1.2641초 | 0.9304초 | 약 26% 감소, 표·payload 복원 동일 |

측정은 이 환경과 시험 입력 기준이다. 모든 부문·실행 환경에서 같은 속도나 한 응답 내 완료를 보장하는 수치는 아니다. 브라우저 최종 측정은 대형 CRM 검사와 동시에 실행했다.

- 전체 회귀 **122개 통과**. 신규 체크포인트/캐시 무효화/실패 후 재개/출력 보호/예외 진단/렌더 입력 검사 포함.
- 정상 설계는 prepare 후 design 작성, 백그라운드 run만으로 HTML·Excel 생성부터 최종 인증까지 통과했다. 같은 입력의 재호출은 기존 통과 결과를 사용했다.
- 기존 CRM Excel+HTML 준비 결과는 업무357개, Lv.5 123개, 상위 단계8개로 유지됐다.
- 대형 기존 CRM HTML도 **108개 화면·580개 상세 창**을 약75초에 검사했다. 정상 처리하고 종료했으며, 기존 연결선 문제를 실패로 판정했다: 근접 선141건, 비직각선1건, 최대 중첩구간16건(혼합형2건). 실제 JavaScript 예외는0건, 별도의 작업자 실패 요약은7건이다. 검사량을 줄여 통과시키지 않았다.
- 해당 기존 CRM의 Agent 페이지12개를 별도로 확인했다. 런타임·콘솔·숨김 잘림 오류는0건이었다. B7은1280px 화면에서52px 가로 스크롤이 필요했지만, 팀에서 본 잘림과 동일한 현상인지는 확인할 수 없다.
- 동일한 설계 JSON 기준 렌더링 데이터·Excel 표의 동등성을 검증했다. LLM이 새 설계를 작성할 때 판단까지 매번 동일해진다는 의미는 아니다.

## 클라이언트 사용

SKILL.md를 진입점으로 사용한다. 패키지 안의 예제는 스키마·테스트용이며 실제 CRM 입력을 대신하지 않는다.

```bash
python scripts/pipeline.py prepare --excel input.xlsx --source-html input-asis.html --spec 3 --work work/crm
# work/crm/design.json에 업무 설계·근거·설명을 작성한다.
python scripts/pipeline.py run --work work/crm --output outputs/crm --background
python scripts/pipeline.py status --work work/crm
```

중단 후에는 prepare부터 반복하지 않고 같은 work에서 run으로 이어간다. 실제 오류가 남아 있으면 diagnostics.json과 QC repair 보고서를 보고 해당 부분을 수정한다. 입력·설계가 바뀌면 새 검사 대상이며, 실행 한도 때문에 검사를 생략하거나 후보를 최종본으로 표시하지 않는다.

이 수정은 팀의 미제공 후보에 남은6개 오류·B7 잘림을 해결했다고 주장하지 않는다. 다음 실행은 오류 원인을 좁힐 진단과 재개 상태를 남긴다. 플랫폼이 프로세스 실행 자체를 차단하거나 환경을 종료하는 경우까지 스킬이 해제할 수는 없다.
